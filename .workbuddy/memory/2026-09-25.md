## 修复「手动调速过一会儿恢复默认」（风扇控制页）

用户反馈：自定义散热后，过一会儿界面刷新就回到默认转速。

`MODE_FAN_DEFAULTS[perfMode]`，且有一个 `useEffect([perfMode])` 在模式变化时把滑块重置为模式默认值 ——
**从不读回后端已持久化的值**。后端其实早就存好了（profile overrides 的 `fan.largeRpm/smallRpm`，
`/api/overrides` 会返回，`/api/fan/status` 也能读）。所以只要 `settings.mode` 变化
（游戏自动切换 auto_switch / 热键切档 / 配置栏切配置 / 重开应用 / 切 Tab 重挂载），滑块就被冲掉。

  删掉自动重置 effect；拖动时 `saveOverride` 立即更新 store（UI 跟随）+ 250ms 尾随防抖
  POST `/api/fan/set-target`（避免一次拖动打出十几个 POST + 配置文件写盘）；

  每个参数行加了「自定义 / 模式默认」标记，并把模式默认值显示在副标题里。
- `src/index.css`：新增 `.fan-tag` / `.fan-manual-actions` / `.fm-state`。
- `server/api/Program.cs`：`FanRpmRange()` 旧实现只认裸模式名，前端传 `cfg-office` 时会落到兜底
  区间 `(0,4400,0,8200)`，「可调范围随散热模式变化」的模式钳位其实从未生效。新增

## 环境坑：git ref 写入被静默吞掉（重要）

在 Bash 工具里跑 `git commit` / `git update-ref` 时，**分支 ref 的写入会被静默丢弃**（命令返回 0，
但 `.git/refs/heads/<branch>` 没落盘）。后果极其严重：`git commit` 变成创建**无父节点的 root commit**，
本地分支指针丢失（`git log` 报 "does not have any commits yet"）。

本次因此把 `fix/memory-v2-integration` 打坏过一次，恢复步骤：
1. 原始提交对象仍在 → `git cat-file -t e348d4b` 可验证；
2. 用**普通 shell 重定向**写 ref（可用）：`printf '%s\n' <sha> > .git/refs/heads/fix/memory-v2-integration`
   （`git update-ref` 不行，加不加沙箱都不行）；
3. `git read-tree <sha>` 复位索引（不碰 ref），工作区改动保留；
4. 提交改用 `git commit-tree <tree> -p <parent> -m <msg>` 生成提交对象（不写 ref），
   再手动写 ref 文件；最后 `git push`（push 正常）。

另：`deploy.ps1` 在 PowerShell 工具会话里会因 `gen-build-info.ps1` 调不到 `git`（`$LASTEXITCODE≠0`）
而在第 1 步就 abort；且 deploy.ps1 第 18 行错误分支里的 `Pop-Location` 没有配对的 `Push-Location`。
本次改为手工执行 deploy.ps1 的 1~3 步（bash 复制 dist → wwwroot + 写 version.txt/build-info.json）。

### 25249 RPM 脏数据（server/hal）
- 现象：风扇控制页「大风扇」实测显示 25249 RPM / 100%（物理上限 4400）。
- 成因（EC 读取路径）：`CpuFanRpm` 用两次独立 `ReadEc(0x9D)` / `ReadEc(0x9E)` 拼 16 位值，
  两笔事务之间会被其它 EC 访问插入（遥测 250ms 轮询、FanCurveService Tick、ParameterGuard、
  `/api/fan/status`），可能拼出跨固件刷新的残缺值，或读回上一笔事务残留在输出缓冲的数据。
  且只判 `val != 0`，没有任何上界校验，脏值直接进遥测 → UI。
- 修复：`DriverBridge.ReadEcPair(reg)`（同一把锁内成对读，lock 可重入）；
  HAL 新增 `ReadValidatedFanRpm(baseAddr, maxRpm, which, ref lastGood)`：
  丢弃 0 与 > FanLargeMax/FanSmallMax 的样本、重试 3 次、全失败回退 Last Known Good，
  超限样本写 `FanRpm` 分类日志（30s 节流）。
  注意上界用 FanLargeMax(4400)/FanSmallMax(8200)，不是曲线里那个 ~3000 的「手动可控上限」，
  否则会把合法的更高转速误判成脏数据。
- 前端 `FanControl.jsx` 加显示层兜底：读数 > max 或 =0 时显示 `—` / `读数无效`。
- **未做的（需实机验证，故意留着）**：DriverBridge 的 EC 事务没有做 ACPI IBF/OBF 握手
  （只靠固定 Sleep），而且 WMI ACPI 通道与 0x62/0x66 端口事务没有互斥 —— 这两点是脏读的深层来源，
  改动会影响所有 EC 读写（含风扇写入、ITSM），必须在实机上验证后再动。

## 第五轮：安装包构建成功（关键突破 + 两处重要订正）

### 突破：根因是「工具会话的进程环境被裁剪」
- Bash 工具会话里 `PATHEXT` / `SystemRoot` / `windir` / `ComSpec` / `APPDATA` / `ProgramData` **全是空**。
- 后果 1：`dotnet <dll>` 直接崩（`EnvironmentProvider.get_ExecutableExtensions()` NullReferenceException，缺 PATHEXT）。

- 解法：调用前显式补齐一整套 Windows 环境变量（`PATHEXT`、`SystemRoot`、`windir`、`SystemDrive`、

  `ProgramFiles`/`(x86)`/`ProgramW6432`、`CommonProgramFiles`、`TEMP`、`TMP`，以及
  `Path = Machine + User` 注册表值）。补齐后 `dotnet nuget list source` 正常返回。
- 我早先还试过 `env ProgramData=... dotnet` 之类的零散补法 —— **不够**，必须成体系地补。

### 订正：「PowerShell 工具会话无法启动任何外部 exe」是错的

### 关键订正：overrides 有**三套**字段名，我上轮写错了其中一处

## 第十二轮：新发现一个缺陷 —— 被拒请求仍写硬件

回归测试 [3] 打 `POST /api/fan/set-target?mode=__nonexistent__` 返回 **400**（符合预期），
但日志显示：

```
[fan/set-target] ← large=3000
[FanEC] EC直写 0x5E=30 (大风扇 3000RPM, mode=__nonexistent__)   ← 硬件已被改
[overrides] ✗ 未知配置 id '__nonexistent__'，已拒绝写入（未落盘）  ← 之后才拒绝
```

**根因**：`/api/fan/set-target` 先调 `ApplyFanSpeed(...)` 再校验 mode id。
**影响**：无效 mode 的值会以**兜底区间 (0,4400)** 落到硬件，**绕过模式钳位**。
这是第 1 轮"overrides 静默成功"修复的遗留 —— 只补了返回值，没调整校验顺序。
已在 `regression-api.js` 里加 [3b] 检测项（WARN，不计入失败，等修）。
**修法**：把 `SavePerfOverrides` 的校验提到 `ApplyFanSpeed` 之前，或先 `ResolveThermalKeyOrNull` 校验再下发。

## 第十三轮：排查 CPU 温度偏高（用户报「97°C，没清灰也不至于这样吧」）

### 用数据排除的可能
| 假设 | 结论 | 依据 |
|---|---|---|
| 是我们这次改动导致的 | **否** | 09-24 16:24 最早的记录就是 77–92°C，中位 86°C |
| CPU 负载高 | **否** | 进程 CPU 占用合计约 7%（`% Processor Utility` 报 33% 是睿频虚高） |
| 电源计划把 CPU 钉在高频 | **否** | 平衡方案，`PROCTHROTTLEMIN=5%`、`MAX=100%`，正常 |
| 风扇没转 / 转速读错 | **否** | 大扇 3400–3900、小扇 6700–7200 RPM，且随设定变化（改设定它就跟着变） |
| EC 温度传感器完全失灵 | **大概率否** | 有 70→99°C 的 29°C 动态范围，说明在跟踪真实变化 |

### 指向"CPU 热传导退化"的三条关键证据
1. **8 小时数据里最低温度是 70°C**，多数低点是 75–77°C。
   即使 CPU 只跑 2.79GHz、风扇 3472 RPM 也有 **75°C**（健康机器此时应 50–65°C）。
2. **加风扇几乎没用**：风扇 3100→3850 RPM，温度无变化；温度-转速相关系数 **r≈0.08**。
   若是鳍片积灰堵风道，加大风量应有效果；**"风量上去温度不动"说明热量传不到鳍片**
   → 瓶颈在 die → 散热器 这一段（硅脂干化/失效）。
3. **GPU 空闲 59°C，CPU 97°C，同机箱差 38°C** → 是 CPU 散热路径的问题，不是整机风道。

**结论**：最可能是 **CPU 硅脂干化**（积灰会加重但非主因）。建议清灰 + 换硅脂，
并用 HWiNFO 之类独立工具交叉验证温度读数。

### 顺带发现的代码弱点
**RPM 路径加了物理上限守卫**（`ReadValidatedFanRpm`，25249 > 4400 会被丢弃），
**但温度路径没有上界校验** —— `CpuTemperature` 只判 `>0 && <128` 就直接当摄氏度返回。
若 EC 0x1C 出现脏读（和 25249 同源的风险），一个 100~127 的假值会被当合法值放行。
可考虑给温度也加上界/交叉校验。

### 排查用到的命令（可复用）
- 进程 CPU 占用：`Get-Process` 取 `.CPU` 前后差值 ÷ 采样秒数 ÷ 逻辑核数。
  **注意 `% Processor Utility` 会因睿频虚高，不能直接用**。
- `powercfg /query SCHEME_CURRENT SUB_PROCESSOR PROCTHROTTLEMIN`（PowerShell 工具里跑 powercfg 无输出，
  用 **bash 调 `/c/Windows/System32/powercfg.exe`** 并补 `PATHEXT`/`SystemRoot` 才有输出）。
- 日志侧的温度/转速统计用 awk 从 `[Telemetry]` 行直接算，不用额外工具。

## 第十四轮：修两个"硬件写入路径"缺陷 + 打 fix.7 安装包

### 修的两个缺陷

1. **`POST /api/fan/set-target` 被拒的请求照样写硬件**（`server/api/Program.cs`）
   旧实现先 `ApplyFanSpeed` 下发、后 `SavePerfOverrides` 校验。未知 mode id 虽然返回 400，
   硬件已经用 `FanRpmRange(null)` 的兜底区间 (0,4400) 写过了 —— **模式钳位被整个绕过**。
   改法：校验/落盘提到下发之前；下发复用钳位后的值（原两处各自钳一次，有漂移风险）。
   错误文案补"也未下发硬件"。

2. **`CpuTemperature` 缺上界校验**（`server/hal/HardwareAbstractionLayer.cs`）
   只判 `>0 && <128` 就返回 → 100~127 的 EC 脏读会被当合法摄氏度放行。
   对齐风扇路径：上界 115°C + 重试 3 次 + `LogCpuTempGarbage` 30s 节流。

### 关键方法论：非提权也能起 3101 做验证（可复用）

`Douzhanzhe.API.exe` 内嵌 manifest `requireAdministrator`，工具会话在 Medium 完整性级别
（`whoami /groups | grep S-1-16-8192`）→ 直接跑报 `Permission denied`。
**绕法：`dotnet Douzhanzhe.API.dll --urls=http://127.0.0.1:3101`**（走 dotnet host 不走 exe manifest）。

非提权实例的能力边界：
- HTTP 层（守卫/overrides/钳位/令牌）✅ 回归测试全跑

- `GET /api/telemetry`、`/api/system/info` ❌ 阻塞/为空（HAL 读路径不可用）
