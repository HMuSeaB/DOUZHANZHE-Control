### 两处残留 + 为什么不改

**1. `/api/overrides/clear` 忽略 `SavePerfOverrides` 返回值**（`Program.cs:1966`）
未知 mode 时落盘静默失败，但硬件清理照跑，最后返回 `ok:true`（假报成功）。
**不改的理由**：`mode` 解析是 `IsNullOrWhiteSpace(req.Mode) ? CurrentMode() : req.Mode`。
若用户曾把「当前模式」设成一个后来被删除的自定义配置，前端面板的「恢复默认」会带上这个
失效 mode → 一旦硬拒绝（400），`clearOverrides()` 里 `if (!res.ok) throw` 会直接抛错，
**反而把原本能降级工作的按钮变成报错**。收益（只有非法调用者能触发）远小于回归风险。

**2. `/api/overrides/switch` 完全不校验 mode**（`Program.cs:1869`）
一进来就 `SetCurrentMode(req.Mode)` + `ApplyThermalMode(...)`，未知 mode 会把 `CurrentMode()`
污染成非法值（此后所有 `SavePerfOverrides(..., null)` 都会失败）。
**不改的理由**：`switchMode()` 在**应用启动时**就会被调用（`useControlState.js:227`，
用持久化的当前模式），且同样 `if (!res.ok) throw` 且无 catch。
硬拒绝会让「持久化模式指向已删除配置」的用户**开不了应用**。当前的优雅降级是对的。

→ 结论：这两处是**有意的容错差异**，不是漏修。已确认前端所有调用点（`clearOverride`/
`switchMode`）传的都是合法 `settings.mode`，正常路径不受影响。
若将来要收紧，正确做法是**让失败可见而非拒绝**（记日志 + 响应带 `persisted:false`），
且必须在同一版里同步处理前端 `throw`。

### 硬知识 1：静默安装会**弄丢开机自启**

`[Tasks]` 里 `autostart` **没有 `checked` 标志** → Inno 静默模式下默认**不勾选**；
而 `CurStepChanged(ssPostInstall)` 在「未勾选」分支会 **`schtasks /Delete /TN "DouzhanzheControl"`**
并把 `auto-start-opts.json` 写成 `{"enabled":false}`。
用户当前该文件是 `{"enabled":true}` → **静默装会把自启关掉**。
→ 要么走 GUI 向导（勾着「开机自动启动」），要么加 `/TASKS="autostart"`。

### 硬知识 2：安装程序**必须由用户手动启动**

`PrivilegesRequired=admin`。从工具会话里 `Start-Process -Verb RunAs` 两次都「返回成功但进程没起」
（第一次沙箱内、第二次关沙箱，`tasklist` 无 `DouzhanzheConsole*`、无 `consent.exe`、`%TEMP%` 无
`Setup Log*.txt`）→ 沙箱/提权链路把 GUI 安装器拦掉了。**别在工具里启动它**，交给用户双击。

### 安装器其他关键行为（读 .iss 得到）

- `ssInstall` 会 `taskkill` Shell + API → **当前实例会被关掉**；装完 `[Run]` 会用**继承的管理员令牌**
  重新拉起程序（`postinstall` 且**无** `skipifsilent`）→ 所以 GUI 装完不需要二次 UAC；
  而**静默装不会拉起程序**（有 `skipifsilent`），得自己再启动一次（Shell 是 requireAdministrator，会再弹 UAC）。
- **用户配置不会被覆盖**：`[Files]` 有 `Excludes: "...config\*..."`。
- 会删 `wwwroot\assets` 与 WebView2 的 Cache/Code Cache/GPUCache/Service Worker（避免旧 bundle 被缓存）。
- 会跑 `PawnIO_setup.exe -install -silent`（`Check: IsAdminLoggedOn`，无 `skipifsilent`，静默也会装）。

### 新发现（既有 bug，非本轮引入）：TaskScheduler 版本冲突 → UI 自启开关 500

**证据链**：
1. 日志 `[API] [TaskScheduler] UnobservedTaskException: Could not load file or assembly
   'Microsoft.Win32.TaskScheduler, Version=2.12.2.0'` —— 累计 77 次，**最早 2026-09-25 01:25**。
2. 程序集版本对比：
   - `server/api/Douzhanzhe.API.csproj` → `TaskScheduler 2.12.2`（AssemblyVersion **2.12.2.0**）
   - `server/shell/Douzhanzhe.Shell/Douzhanzhe.Shell.csproj` → `TaskScheduler 2.11.0`（**2.11.0.0**）
   - `server/api/bin/build/` = 2.12.2.0 ✅，但 `dist/publish/api/` = **2.11.0.0** ❌
3. 成因：`build-installer.ps1` 的合并步骤把 Shell 输出并进 `dist/publish/api`，
   **Shell 的 2.11.0 DLL 覆盖了 API 需要的 2.12.2**。而 `.iss` 的 `[Files]` 直接拷 `dist/publish/api/*` → 装机目录拿到的就是 2.11.0.0。
4. 实测影响：`POST /api/auto-start` → **HTTP 500**（**设置页的「开机自动启动」开关是坏的**）。
   注意不是代码里那个 `catch → {ok:false}`：`TaskService` 的**类型解析失败发生在 JIT 期**，
   异常在进入方法内 try 之前就抛出，直接冒到全局处理器 → 500。
   `GET /api/auto-start` 只读缓存所以看起来正常，但它那个「后台查计划任务校验缓存」的 Task 也永远失败。
5. **归因**：Shell 那行 2.11.0 是 `20c1b9b`（**2026-06-08**）引入，本分支未改动 → **既有 bug，与本轮修复无关**。
   自启本身能用，是**安装器的 schtasks 通道**建的（不走 API），所以没暴露。

**修法（待用户决策）**：把 Shell 的 `TaskScheduler` 从 2.11.0 对齐到 2.12.2（两者 minor 差异，
Shell 只在 `Program.cs:184` 的提权回退路径用它）。改完需重打包 → fix.9 → 用户再装一次。

### ⚠️ 本轮最重要的一条订正：**不能用文件大小判断程序集版本**

我一开始按大小判版本（334848 = 2.11.0.0 / 335360 = 2.12.2.0），**错了**。
`"2.11.0.0"` 与 `"2.12.2.0"` **等长**，改版本号**不改变文件大小** —— 实测：
- NuGet `2.11.0` 包的 DLL = 2.11.0.0，334336 字节
- NuGet `2.12.2` 包的 DLL = **2.12.2.0**，**334848 字节**
- 装机 fix.8 的 DLL = 2.11.0.0，**334848 字节**（与 2.12.2 包**同大小、不同版本**）

必须读 `AssemblyName`。为此写了 `tools/check-dll-versions.ps1`。
